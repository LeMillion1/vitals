Role model and guardrails

ZITADEL proves identity

It owns passwords and login. Vitals owns member, doctor and trainer meaning.

Choice is not verification

A self-declared doctor or trainer can submit a profile but cannot open a patient.

Role is not consent

Patient access still requires a verified profile, exact relationship, current consent and scope.

One-time server intent

The browser carries only an opaque UUID. Account type, email and provider claims stay server-side.

Existing accounts are stable

Opening a new registration intent must never add or replace roles on a linked identity.

Email verification remains explicit

Password-only beta can create accounts, but address-bound care invitations require a separately verified mailbox.

Acceptance checklist

Public path

At phone and desktop widths, a visitor can create each account type without a shell command.

Replay safety

Expired, replayed and mismatched intents fail uniformly and create no account.

Isolation

A new member sees an empty personal record; a new professional sees no patient and owns no record.

Professional review

Doctor and trainer land directly in simple profile onboarding and then a clear pending state.

Admin UI

An administrator can open or pause Vitals registration and review professionals from the browser.

Production test

The complete flow is verified in Compose and in a clean browser session against the deployed build.

This map is the implementation checklist. A screen is not complete until its lane, copy, guardrail and acceptance item all agree with the running service.
