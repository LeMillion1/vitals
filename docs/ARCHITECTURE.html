C4 · Level 1

What it is

Vitals is a health-data service, self-hosted behind a VPN. It pulls from the devices and services that already hold fragments of a record, keeps every upstream response verbatim, and turns those into facts it can chart, compare and reason about.

The ownership conversion is in force: medical rows belong to a named health subject, explicitly and enforceably. Product work remains around onboarding, professional workflows, scoped external grants and operational hardening.

C4 · Level 2

Containers

One FastAPI process serves the web UI, the MCP endpoint and the external read API. An APScheduler loop inside it runs sixteen jobs. Everything durable is in PostgreSQL; Redis holds only what can be lost without consequence.

The core of the conversion

The ownership graph

Before, a row was simply in the database, and that was enough to identify it as the owner's. The conversion replaces that with four explicit roots, each answering a different question about a row.

RootQuestion it answersAbsent means

actor_user_idWhich human entered it?A system or scheduled job did
integration_connection_idWhich account did it arrive through?Nobody's device — typed in by hand

Invariant

A null actor is legitimate — a migrated row or a scheduled sync genuinely has no human behind it. A row that names an actor but no subject is not old data, it is broken provenance, and every reader reports it rather than passing over it.

Data lifecycle

Raw, fact, artifact

Nothing upstream is discarded. Every provider response and every uploaded document lands in raw_payloads as JSONB before anything is derived from it, so a parser improved next year can recover columns this year's parser dropped — without a network call.

Invariant

A fact's provenance is a link to its own raw payload, and both must name the same subject. A fact pointing at somebody else's payload is refused; a fact pointing at an unstamped payload mid-backfill is simply out of scope, which is what a half-migrated table looks like from inside.

Write path

How a write happens

A domain service will not accept a subject on its own. It takes the subject and the conflict decision that authorized the write, as one capability minted earlier in the same transaction. The signature enforces what a comment used to ask for.

Lock order

Every write path takes the same locks in the same order — governance advisory, then the active-weight advisory, then the subject row, then the connection row, then the domain's own rows. The order is uniform because a Garmin daily bundle can carry a weigh-in, so two independent sync paths can reach the weight tables at once; the previous ordering produced a real deadlock under PostgreSQL.

Read path

How a read is bounded

Three boundaries, deliberately independent. Each would be sufficient on a good day; together they mean a mistake in one is not a breach.

Fails closed

An unbound session sees nothing, not everything. current_setting returns NULL when the application forgot to say whose request it is serving, the policy comparison is NULL, and no row qualifies. Getting the boundary wrong shows up as an empty page, never as somebody else's data.

FORCE is the operative word: PostgreSQL exempts a table's owner from its own policies, and the application connects as the owner. Roles that must see across subjects — the migration runner, the ownership backfill jobs, the platform control plane — are exempt by role attribute. That is deliberate: a backfill that could not see an unstamped row could not stamp it.

Work that belongs to nobody in particular

Not every transaction is somebody's. A doctor opening a shared report has no account here and is not meant to need one — the token in the URL is the authorization, and the application checks it before reading anything. Four scheduled jobs are the same shape: the share purge, the AI invocation reconciler, the historical delivery reconciler, and the care-push dispatcher each sweep across every subject with no person to act as.

Under the subject comparison alone, installation-wide jobs see nothing and report success. The RLS contract therefore admits a second explicit scope, vitals.platform_scope, alongside the subject policies. A contract test enumerates every application caller allowed to enter it.

Narrow by construction

Transaction-local like the subject binding, so a scope that reads across everybody cannot ride a pooled connection into the next request. Asked for by name through enter_platform_scope, never drifted into. Opened only by the exact string on, so a stray or truncated value closes. And all nine call sites are enumerated by a contract test — a tenth is something a reviewer reads, not something that accumulates.

The line that keeps it honest: this is for work that has no subject, not work that failed to find one. A path that merely forgot to resolve its subject should see nothing — that is the boundary working — and its fix is to bind, never to declare itself the installation.

Cross-domain safety

The conflict engine

Rules are data, not code. Each domain registers a resolver that reports its current state for one subject on one date; the engine evaluates active rules across domains before a write lands, and turns a violation into a block, a warning, or a passive alert.

Where the service is

The conversion

The order matters and was corrected twice by practice. Columns had to exist before anything could fill them; the composition layer had to learn to pass a subject before a leaf service could demand one; and the conflict resolvers had to go after the leaves, not before, because their unscoped arm was only reachable from inside a leaf.

PR-01

Identity and support foundationmerged

Users, roles, health subjects, time-boxed support grants, audit events. Roles are additive and never a data grant on their own.

PR-02

Owner bootstrap and the policy vocabularymerged

The existing installation gets a named owner and subject at startup. AccessContext and is_allowed are written — and stay unused for two PRs.

PR-03

Ownership expansion and backfillmerged

Nullable ownership columns on every table, dual-write from every path, eighteen resumable backfill phases, then scoped unique keys installed beside the global ones and the global ones dropped. Two people can now share a weigh-in date.

PR-04

Scoped services, the contract, and RLSmerged

266 functions that would read across the whole installation when the caller omitted a scope, reduced to zero. The unscoped conflict path deleted. Every ownerless writer retired. Then NOT NULL on 39 columns, and FORCE row-level security on every table that names a subject.

PR-05

OIDC authentication and local sessionsmerged

OIDC Authorization Code + PKCE, immutable provider identities, revocable application sessions, upstream logout and recent-authentication step-up are implemented. The safe invitation-recipient handoff is merged; supported operator admission and delivery remain active work.

PR-07 …

Relationships, consent, professionalsmerged

Professional verification, invitations, relationships, versioned consent, records and patient-visible conversations now supply the grants evaluated by the policy engine. Workflow and UI completeness remain active work.

What "closed" turned out to mean

A domain counted as closed when its subject was mandatory, its include_legacy_unowned escape hatch was gone, and — the part that kept being missed — the branch that quietly adopted an unowned row on the way past had been removed. An unowned row then stays unowned and stays invisible, which is the whole point.

Rule the closures follow

Adoption stays only where it is the operation's purpose — the nightly sweep that turns an unowned upload into an owned scan — and never where it is a convenience on the read path. Even then it is decided per row, from that row's own roots, rather than from a flag the caller passed in.

Deleted, not scoped

Some code had no scoped equivalent because it only made sense with one person in the database: the zero-subject daily brief, Garmin's unscoped sync and pulse, Hevy's, the raw upsert that belonged to nobody, and the VCF adapter that stored a genome as an ownerless payload. Each had an owned twin the live callers were already using. Scoping them would have preserved a path nothing should take.

Operations

The cutover

Upgrading an existing installation is not one alembic upgrade head. It is three parts, and the middle one is an application job rather than a migration.

On PostgreSQL each column is proven with a NOT VALID check that is then validated before SET NOT NULL takes over from it. Validation takes a weaker lock than the alter would, and PostgreSQL accepts the validated check as proof — the difference between a pause and an outage on a table holding a couple of thousand samples for every day ever synced.
