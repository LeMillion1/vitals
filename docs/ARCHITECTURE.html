C4 · Level 1

What it is

Vitals is a self-hosted health-data service served through HTTPS. Every account-protected route requires application authentication; anonymous routes are explicitly enumerated, and sensitive ones use a surface-specific token, signature or secret boundary. It pulls from the devices and services that already hold fragments of a record, keeps the complete current upstream input, and turns those responses into facts it can chart, compare and reason about.

The ownership conversion is in force: medical rows belong to a named health subject, explicitly and enforceably. The OIDC boundary and self-hosted ZITADEL stack are implemented; production remains on legacy password login only until the public identity DNS/TLS route, OIDC application and first-owner binding pass their cutover gates.

C4 · Level 2

Containers

Production runs two independent processes from one immutable image. The web process serves FastAPI, HTMX, MCP and the external API but never starts APScheduler; the worker process publishes no HTTP port and owns all sixteen application jobs. One-shot migration and role-provisioning services run before either. Durable relational and control metadata is in PostgreSQL, medical file bytes live in private storage, and Redis carries recoverable coordination state.

Personal portability v2 is an owner-only encrypted archive boundary over this graph: it authenticates the archive, maps credential-free connection descriptors explicitly, stages verified private resources, and commits replacement plus an exact replay receipt atomically. Installation recovery is separate and shipped: the health bundle pairs PostgreSQL, Garmin session, private files and legacy uploads, while ZITADEL uses an independent SQL+Login-PAT bundle and separately escrowed master key. Both destructive restore paths are rehearsed; automated offsite repositories remain operator-provided.

The core of the conversion

The ownership graph

Invariant

A null actor is legitimate — a migrated row or a scheduled sync genuinely has no human behind it. A subject-owned clinical fact that names an actor but no subject has broken provenance; platform, account and audit rows follow their own explicit ownership classes.

Data lifecycle

Raw, fact, artifact

The complete current upstream payload is persisted before normalization. A repeated scoped external key refreshes that row rather than retaining every historical response version; the stored payload can still be reparsed later without a network call.

Invariant

A fact's provenance is a link to its own raw payload, and both must name the same subject. A fact pointing at somebody else's payload is refused; a fact pointing at an unstamped payload mid-backfill is simply out of scope, which is what a half-migrated table looks like from inside.

Write path

How a write happens

A conflict-governed clinical service takes the subject and the conflict decision as one capability minted earlier in the same transaction. Other writes use their own typed boundary: care uses AccessContext, timeline mutations use WriteIdentity, and account/control operations use dedicated authenticated inputs rather than pretending every mutation has a clinical conflict rule.

Lock order

Generic conflict preparation fixes the order governance advisory → subject row → relevant actor or owner rows. Weight writes insert the active-weight advisory after governance and before the subject; provider ingestion locks a validated connection and domain rows where that path requires them. These are reviewed partial orders, not one universal lock list. A Garmin daily bundle can carry a weigh-in, so two independent sync paths can reach weight tables at once; inconsistent ordering previously produced a real PostgreSQL deadlock.

Read path

How a read is bounded

Three gates bound an ordinary clinical read. Application authorization and scoped services prevent accidental widening in code; PostgreSQL RLS is the independent data boundary that also constrains an ad-hoc query.

Break-glass is intentionally not unioned into this ordinary policy context. Its dedicated service verifies one exact session, holder, subject, two independent approvals, read-only domain scopes and TTL, then its own fixed projection binds that subject for RLS. No care consent, support grant, role, MCP capability, note, plan, conversation or file surface is inherited into the emergency decision.

Fails closed

An unbound restricted runtime session sees no subject-protected rows. current_setting returns NULL when the application forgot to bind a subject, the policy comparison is NULL, and no protected row qualifies. Global catalogs and explicitly classified account/platform controls remain governed by their own boundaries.

FORCE is the operative word: production web and worker use distinct non-owner logins with neither SUPERUSER nor BYPASSRLS. The schema-owner login never enters a long-lived runtime; it is reserved for migration, backfill, role-provisioning, backup and bounded operator maintenance. Cross-subject worker transactions require both transaction-local vitals.platform_scope=on and membership in one database-specific NOLOGIN capability role; web has no such membership, so setting the GUC alone grants it nothing.

Work that belongs to nobody in particular

Not every transaction is somebody's. A shared-report URL token identifies one frozen artifact, but reading it additionally requires its report password and database-side token attestation. Five scheduled jobs are installation-wide by design: share purge, AI invocation reconciliation, delivery reconciliation, care-push dispatch, and registration-admission retention each sweep across subjects with no person to act as.

Under the subject comparison alone, installation-wide jobs see nothing and report success. The RLS contract therefore admits a second explicit scope, vitals.platform_scope, alongside the subject policies. A contract test enumerates every application caller allowed to enter it.

Narrow by construction

Transaction-local like the subject binding, so a scope that reads across everybody cannot ride a pooled connection into the next request. Among restricted runtime logins it is effective only for the worker capability member. The AST contract enumerates 9 permitted caller functions; bounded owner/operator one-shots already run outside the restricted RLS boundary.

The line that keeps it honest: this is for work that has no subject, not work that failed to find one. A path that merely forgot to resolve its subject should see nothing — that is the boundary working — and its fix is to bind, never to declare itself the installation.

Cross-domain safety

The conflict engine

Rules are data, not code. Each participating domain registers a resolver that reports its current state for one subject on one date; the engine evaluates active rules across the 9 registered conflict domains before a governed write lands, and turns a violation into a block, a warning, or a passive alert.

Where the service is

The conversion

The order matters and was corrected twice by practice. Columns had to exist before anything could fill them; the composition layer had to learn to pass a subject before a leaf service could demand one; and the conflict resolvers had to go after the leaves, not before, because their unscoped arm was only reachable from inside a leaf.

PR-01

Identity and support foundationmerged

Users, roles, health subjects, time-boxed support grants, audit events. Roles are additive and never a data grant on their own.

PR-02

Owner bootstrap and the policy vocabularymerged

The existing installation gets a named owner and subject at startup. AccessContext and is_allowed are written — and stay unused for two PRs.

PR-03

Ownership expansion and backfillmerged

Nullable ownership columns on every table, dual-write from every path, 19 resumable backfill phases, then scoped unique keys installed beside the global ones and the global ones dropped. Two people can now share a weigh-in date.

PR-04

Scoped services, the contract, and RLSmerged

266 functions that would read across the whole installation when the caller omitted a scope, reduced to zero. The unscoped conflict path deleted. Every ownerless writer retired. Then NOT NULL on 39 columns, and FORCE row-level security on every table that names a subject.

PR-05

OIDC authentication and local sessionsmerged

OIDC Authorization Code + PKCE, immutable provider identities, revocable sessions, upstream logout, recent-auth step-up, operator invitations/requests and bounded applicant retention are implemented. Production remains on legacy password login until public ZITADEL and the first-owner binding pass the cutover.

PR-07 …

Relationships, consent, professionalsmerged

Professional verification, invitations, relationships, versioned consent and records supply the grants evaluated by the policy engine. Every live relationship resolves to one canonical conversation, created lazily on first access; historical topic threads remain readable. Provider-side identity invitation and recovery delivery are still operational steps.

What "closed" turned out to mean

A domain counted as closed when its subject was mandatory, its include_legacy_unowned escape hatch was gone, and — the part that kept being missed — the branch that quietly adopted an unowned row on the way past had been removed. An unowned row then stays unowned and stays invisible, which is the whole point.

Rule the closures follow

Adoption stays only where it is the operation's purpose — the nightly sweep that turns an unowned upload into an owned scan — and never where it is a convenience on the read path. Even then it is decided per row, from that row's own roots, rather than from a flag the caller passed in.

Deleted, not scoped

Some code had no scoped equivalent because it only made sense with one person in the database: the zero-subject daily brief, Garmin's unscoped sync and pulse, Hevy's, the raw upsert that belonged to nobody, and the VCF adapter that stored a genome as an ownerless payload. Each had an owned twin the live callers were already using. Scoping them would have preserved a path nothing should take.

Operations

The ownership cutover

For databases older than revision 0049, ownership conversion is not one alembic upgrade head. The historical three-part sequence below remains the required bridge. The current schema has completed it, advanced through 0085, split migration/web/worker database authority, and health-gated worker before web.

On PostgreSQL each column is proven with a NOT VALID check that is then validated before SET NOT NULL takes over from it. Validation takes a weaker lock than the alter would, and PostgreSQL accepts the validated check as proof — the difference between a pause and an outage on a table holding a couple of thousand samples for every day ever synced.
